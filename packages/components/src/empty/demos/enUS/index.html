Error State anatomy

So core anatomy for empty and error states is the same. It consists of an Illustration, Title, description and  Actions ( CTA’s ).

Illustration : Illustrations are optional—but they’re a great way to add a touch of fun and visual interest while helping users understand their situation.

Title : Should be focused on the situation with clear communication.

Description : This acts like body content and should be focused on explaining the situation in detail along with an additional “link” action if needed.

Primary Actions : Used for the most important actions you want users to take. Should be clear and predictable

Secondary Actions : Used for less important actions such as “Learn more” or “Close” buttons.

Other than these elements Error state component also supports few optional metadata to support scenarios with more complex information.

Error code(Optional): Non mandatory information and to be shown only for the technically expert users and debuggers to easily understand the error types.

Highlighted section(Optional): Non mandatory information and used for highlighting the next set of steps for user to perform as a support for error recovery.

Debug ID & Timestamp(Optional): Non mandatory piece of information but crucial for debuggers for error management.


Empty State Options

We have options for empty state component based on different scenarios where it’s being used.

Each empty state must have a message and a visual element (Illustration or Icon). A call to action is optional though.

Empty Page Scenario

Empty pages generally occur during the first-time use of a product when there is no data created to display yet.

No Search results Scenario

This scenario occurs when a user searches for a specific keyword/item, and no results are found.

No Filter results Scenario

This scenario occurs when no results are found for the applied filters.

Size options

Empty state comes in two sizes: Default and Small

Default size to be used in all the scenarios with sufficient availability of space to host the component.

Small size to be used for small containers and scenarios with less availability of space like View containers, Popovers.

Error State Options

In Error state we have options specifically accommodating different situations like:

  • Error occurred

  • Session Expired

  • Server Error (Error code: 500)

  • Service Unavailable (Error code: 503)

  • Forbidden response (Error code: 403)

  • Page not found (Error code: 404)

Sizes

Error state component also comes in two sizes: Default and Small

Selection of which size to use depends on what type of information you want to show and how much space is available for that.

Alignment

Error state also have options for alignment : Center and Left

Center alignment to be used in all the app related errors or when you have to show error states in various UI containers.

Left alignment to be used only when app is not able to load at all and you have to show error in full screen. Look at the examples shown below for more reference.

Error state representation in:

  1. In app error : Center aligned

  2. Page wide error : Left aligned

  3. Error in sidesheet container : Center aligned

Behaviours

Fixed width & Modular height

We have fixed empty/error state width to 400 px to maintain the sense of consistency.


For Title : Try to fit it in one line. Should be short and on point.

For Body : Can go upto 3 lines max. Try to keep it short and informative, telling the user what’s happening.

Height can be flexible and depends on the content and elements of the component.

Usage Guidelines


Do’s

  • Use short and informative content always. Please avoid providing long paragraphs in body content and long headlines


  • Do use “clear and predictable” tone in primary actions. Users should be able to anticipate what will happen when they click a button


Don’ts

  • Avoid using more than 2 CTA’s ( 1 primary and 1 secondary ), if needed try to accommodate the requirement using “link” action.
